## Order of a pass

1. Merge the branch being measured; batch compile; build the player.
2. Measure the seven scenarios, 3 runs each, in rounds. One thing at a time: no
   compile, test or Editor while a player measures.
3. Attribute: markers, counts, then controlled runs taking one thing away.
4. Commit each small fix with its test **before** the slow runs, then measure the
   stack by commit (below). 5 storm or snow steps took about 10 minutes.
5. Verify, one run of each scenario on the final build, write up.

## What went wrong, and what to do about it

- **Bot runs need a limit of 1500 s.** I gave 700 s, for 480 s of game time at
  better than real speed. It's slower than real time here (about 47 ms a frame
  against 33 ms of game time), so the first two reached frames 14 280 and 14 430
  of 14 400 and were ended with no result line, because the bot writes it only as
  it quits. A third was stopped on purpose. All 3 were redone. Those are in `killed/`.
- **A run that ends inside a slow frame loses that frame.** A fog run's first
  result had 16 frames, worst 296 ms, over 63 s: the one-minute frame was missing,
  because the coroutine finished before the next `Update` could record it. `Update`
  now ends the run. Rule: check that frames × mean is close to seconds.
- **Fog looked like a hang.** `sample <pid> 3 -file f.txt` on the player found
  the cause in a minute even with no symbols for scripts, and is worth doing on
  anything stuck: the native frames named `CreateGameObject` and PhysX.
- **The marker list comes first.** My first guesses had 3 names that don't exist
  (`Physics.Processing`, `Render Thread`, `Terrain.Heightmap.RenderPatches`). The
  `missing=` field on `PERF MARKERS` says which. A recorder finds a marker by name,
  whatever category it's given. `Camera.Render` exists and reads 0 under URP.
- **`PlaytestBot` had no markers** despite the brief; it has `PlaytestBot.LateUpdate`
  and `PlaytestBot.Shot` now. Step 2 added chunk, spawn, water, fog and flame ones.
- **`EditorApplication.EnterPlaymode()` from `script eval` did nothing** in an
  unfocused Editor, and my poll loop waited 10 minutes for it. Use the probe.
- **A flames-off shot from far away proves nothing:** the fire had moved out of
  shot. The close view with a flicker baseline is the real check.
- **`python3` here has Pillow but no numpy.** Plain loops over 1.4 M pixels take
  seconds. `==` in a zsh `echo` is an error; write `--`.
- **Short fog runs mislead.** 60 s showed one long frame and hid the rest, and
  which order they came in: the 300 s run (`fog-long.log`, limit 620 s) showed the
  whole shape. Read frame numbers and `t=` before saying what comes after what.
- **Seed 811 isn't the RC's route** without `playtest/coverage.json` and the RC's
  `run.json`. To check #5 on a Mac, use the `forest` scenario on a cold Metal cache.

Pitfalls:

- **A hitch from compiling shaders only shows once.** The first forest run had 446
  ms frames; the next had none, and it looked random. macOS keeps compiled
  programs in `$(getconf DARWIN_USER_CACHE_DIR)com.anweather.spellchemistryvalley/`
  (`com.apple.metal`, `com.apple.metalfe`). To repeat it, move those aside and put
  them back after. Any hitch that "doesn't reproduce" should be tried cold.
- **A long `Semaphore.WaitForSignal` inside the camera stack names nobody.** It was
  the compile; `-pso-trace` named the shaders by frame number.
- **`sample` over a whole run nearly halved the frame rate** (25 to 37 ms) and
  shows a one-off spike as a few samples only. It's for stuck things.
- **The bot's budgets are work units, not time.** Its water numbers are a batching
  effect; always run `-perf-time-budget` too before calling something a spike.
- **Don't trust a test that shows nothing:** my emitted particles barely drew, so
  the particle half of the pso check proved nothing. Check against a control.
- **A cost list needs its baseline:** the flamewall looked like flames until the
  no-flames run was 77 ms too. Take effects apart one by one.
- **`git commit` and hooks:** step 2 reported a hook refusing subjects over 50
  characters, body lines over 72 and a `Co-Authored-By` naming Claude. Step 3 hit no
  refusal: every commit went through with that line, subjects at 50 or under. The
  repo's hooks are only Git LFS's, so whatever refused wasn't in `.git/hooks`. Not
  explained.
- **`dotnet` isn't on the PATH on the Mac:** `~/.dotnet/dotnet`.

## Step 3: fixes and verification

Raw logs: `.../scratchpad/perf/step3/` (`before/`, `f2` to `f6/`, `f1/`, `after/`, `d/`
for the diagnostic builds; helpers `build.sh`, `run.sh`, `stepm.sh`, `after.sh`, `m.py`).

```sh
# Measure a stack of fixes one commit at a time (each step about 2 min):
git checkout --detach <commit> && build && run   # stepm.sh; git switch back after
# Does a skipped redraw leave a tile wrong? At the end of any scenario:
-perf-water-check     # PERF WATER CHECK tiles=N different=M
# Merge pipeline states with no open Editor (name a copy of the shipped file first):
$U -batchmode -quit -projectPath $WT/unity -executeMethod PsoCollections.MergeFromCommandLine \
   -pso-merge shipped-copy.pso forest-night.pso -logFile merge.log
# EditMode, one authoritative run (190 s); needs no other Editor on that project:
$U -batchmode -projectPath $WT/unity -runTests -testPlatform EditMode -testResults r.xml -logFile t.log
# #5, cold: move the Metal cache aside for the run, delete the new one, put it back:
D="$(getconf DARWIN_USER_CACHE_DIR)com.anweather.spellchemistryvalley"
```

| Stage | Time |
|---|---|
| Merge, compile in batch | under 1 min |
| Player with `-rebuild-yard` after a merge | 141 s |
| Player after a script change | 37 to 53 s |
| Bot, 480 game seconds | 724 s before the fixes, 466 s after |
| Full after set, seven scenarios | about 12 min |
| EditMode in batch | 190 s |
| GUI Editor to ready | 10 s |

Pitfalls:

- **`EditorApplication.delayCall` never ran in an unfocused Editor,** so a quit that way
  left it open and my batch's next build failed at once ("build exit 1 in 0s") while the
  script went on measuring the old player. Quit a GUI Editor with `EditorApplication.Exit(0)`
  directly, and **check it's gone before starting anything**: have a script stop on a
  failed build.
- **A GUI Editor started with `-openfile` opens no scene** for the probe: open it with
  `EditorSceneManager.OpenScene` through `script eval`.
- **The first probe after an Editor starts can fail `no_console_errors`** on Unity's own
  `SearchDatabase` indexing. Read the error, run again.
- **A measured scenario isn't the same scene once the frames are faster:** more ticks
  run in 30 s, so a faster storm gets further into the weather, and its GPU time went
  from 12 to 18 ms on its own. Compare on ticks too, and take a short run as a control.
- **An analyzer error in `Playtest/Editor/` or a tests file only shows in `dotnet build
  core`, not in a Unity compile:** run it before committing (CA1806 on a discarded
  `ToList`, S3776 on a nested test).
- **A check that always passes proves nothing:** break the fix on purpose once and see
  it fail. A 1-cell margin in `CellHeightfield` passed, and rightly; only a tighter
  one showed the test could fail.
- **Before saying a fix broke something, build without it.** The 3 tiles the water
  check found were old: the same tiles differ with the fix taken out.
- **`timeout` isn't on this Mac.** A `grep -r` over `~/Documents/Development` took over a
  minute: search the repo with `git grep`.
- **`git rebase -i --autosquash`
  works unattended** with `GIT_SEQUENCE_EDITOR=true`.

## Measure every time

- The seven scenarios at 1600x900, 3 runs each in rounds, with `-perf-water-check`.
- Each scenario's frames × mean close to its seconds (see the fog pitfall).
- `PERF SPIKE` lines, ticks in the run (6 a second is on pace; storm and fog aren't),
  active chunks, `tick.owed_ms`, `gc_alloc_kb_mean` and `_peak`.
- `forest` on an empty Metal cache, for #5 and any new shader: worst frame, and the
  `PSO WARMUP` line's states and ms.
- `frame_ms_worst` in the bot's `run.json`.
- Play-mode entry through `tools/probe.sh perf --seconds 1`.
